# Colour prompts

Four prompts for AI tools working with ds colour. Each is a ready-to-paste block with a short "what good looks like"
section, so the person using it can tell a good answer from a bad one.

| Prompt | Use it to | The AI must… |
|---|---|---|
| [Build with colour](build-with-colour.md) | build a screen or component | plan roles first, check every pair (including hover and selected), write code with roles only |
| [Review colour use](review-colour.md) | review code or a design before it ships | confirm the checker's findings and find what a checker can't: inherited backgrounds, colour-only meaning, two primaries |
| [Add a colour role](add-a-colour-role.md) | handle "we need a new colour" | look for an existing role first; if none fits, propose one in engine config the build can test |
| [Theme a new brand](theme-a-brand.md) | adopt ds with a different brand colour | set up the config and run the engine; quote numbers only from its output |

## Always attach the rulebook

Every prompt expects `../color.md` — the colour rulebook generated by the engine — in the same chat. It holds the rules
(CR-01 … CR-15), the decision guide, every role with its Light/Dark value, the pair contract and the "not allowed"
list. For tools that handle JSON well, `../color.contract.json` has the same content in machine-readable form.

Regenerate both whenever tokens change (`npm run build && npm run publish` in the engine folder). An AI working from an
old rulebook will pick roles that no longer exist.

## Trust, but check

An AI's answer is a draft. Each prompt names the tool that checks it:

- **Code** → `npm run lint:color -- <files>` reads the source; `npm run audit:page -- <page.html>` renders it in Light and Dark and measures what people see.
- **New roles and brands** → `node src/cli.js <config.json> out/<name>`. The engine solves every shade and measures every pair; it stops if one fails.

See [../tests/](../tests/README.md) for how these prompts were tested and how to test them with your own tool.
