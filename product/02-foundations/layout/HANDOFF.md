# Layout · developer handoff

How to take ds layout from Figma into code and keep it correct. Read the [guide](GUIDE.md) first if you haven't — this page
assumes you know what the breakpoints, the page grid, the panes and the reading width are. A working screen that uses
everything below is in [demo/](demo/index.html): it shows `app.html` in a frame you can set to any width (or drag), with a
density switch and a "show the grid columns" switch, and reads back from inside the frame what the layout resolved to.

---

## What you get

All generated by the engine (`npm run build` → `engine/out/<name>/`). Never edit them by hand.

| File | What it is | Who uses it |
|---|---|---|
| `tokens.css` | Layout variables (breakpoints in em, the page grid per breakpoint, widths, the header per density) and the layout classes: `.ds-page`, `.ds-grid`, `.ds-span-*`, `.ds-measure`, `.ds-tiles`, `.ds-region`, `.ds-shell` | Every web project |
| `tailwind.theme.css` | `md:` `lg:` `xl:` at the same widths (Tailwind's own `sm:` and `2xl:` removed), `max-w-page`, `max-w-reading`, `px-margin`, `gap-x-gutter`, `min-h-header`, `scroll-pt-header`, `w-nav`, `w-aside` | Tailwind projects |
| `tokens.json` | All tokens in the W3C design-token format | Other platforms, Style Dictionary |
| `figma/Layout.Value.tokens.json`, `figma/Responsive.<bp>.tokens.json`, `figma/Density.<mode>.tokens.json` | The layout variables per collection and mode, for Figma | Design |
| `ai/rules/layout.md`, `ai/layout.contract.json` | The layout rulebook and contract for AI tools and the layout checker | AI tools, the layout checker |
| `report.html`, `report.json` | Every layout check (L1–L5), item by item | Reviews, audits |

## Install

The same `tokens.css` as colour, type and spacing — nothing extra to load.

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
<link rel="stylesheet" href="/css/tokens.css">
```

Tailwind v4, in your main CSS file:

```css
@import "tailwindcss";
@import "./tokens.css";
@import "./tailwind.theme.css";
```

## Breakpoints

Mobile first, `min-width` only, in em. The `sm` layout has no query.

```css
.summary { /* sm: the default */ }
@media (min-width: 37.5em) { .summary { /* md, from 600px */ } }
@media (min-width: 64em)   { .summary { /* lg, from 1024px */ } }
@media (min-width: 90em)   { .summary { /* xl, from 1440px */ } }
```

In Tailwind: no prefix, then `md:`, `lg:`, `xl:` — the same widths. Tailwind's `sm:` and `2xl:` don't exist in ds; the layout
checker flags them, and `max-*:` and `min-[…]:` variants too.

**Why em.** A reader who sets a bigger default text size gets the layout of a narrower window: at 32px text a 1280px window
gets the `md` layout, with room for the bigger words. Breakpoints in px would keep the desktop layout and squeeze it.

**JavaScript** reads the same queries: `matchMedia('(min-width: 64em)')`. Never a px width of your own.

## The shell

```html
<div class="ds-shell">
  <header data-shell="header">
    <button type="button" data-shell-toggle="nav" aria-expanded="false" aria-controls="nav" aria-label="Sections">☰</button>
    <a href="/">Product</a>
  </header>
  <nav data-shell="nav" id="nav" aria-label="Sections">…</nav>
  <main data-shell="main" id="main"><div class="ds-page">…</div></main>
  <aside data-shell="aside" aria-label="Help">…</aside>
</div>
```

- **Order is the contract.** Header, start panes (`nav`), `main`, end panes (`aside`) — the shell never draws them in another
  order, so keyboard and screen-reader order always matches what people see. The layout checker fails any other order.
- **Panes go inline at their breakpoint.** `nav` from `lg`, `aside` from `xl` — the widths the build proved fit (check L3).
  Below that, `aside` sits under the main content and `nav` becomes a drawer.
- **Leave a pane out** and its column disappears: each pane's column is sized by the pane in it.
- **The header** has `min-height: var(--ds-layout-header-height)` and sticks to the top in windows at least 30em tall. Keep it
  to one row of controls, so it never outgrows the scroll padding.

**The drawer.** Below `lg` the navigation is hidden — and out of the tab order — until your code sets `data-open` on it. The
toggle's job:

```js
const toggle = document.querySelector('[data-shell-toggle="nav"]');
const nav = document.getElementById('nav');
const setOpen = (open, returnFocus) => {
  nav.toggleAttribute('data-open', open);
  toggle.setAttribute('aria-expanded', String(open));
  if (open) nav.querySelector('a')?.focus();
  else if (returnFocus) toggle.focus();
};
toggle.addEventListener('click', () => setOpen(!nav.hasAttribute('data-open'), false));
document.addEventListener('keydown', (e) => { if (e.key === 'Escape' && nav.hasAttribute('data-open')) setOpen(false, true); });
```

`[data-shell-toggle="nav"]` hides itself from `lg`, where the pane is inline. The drawer leaves at least 48px of the page
visible on a 320px screen.

## The page, the grid and spans

```html
<main data-shell="main">
  <div class="ds-page">                                   <!-- capped at layout.container.max, padded with layout.margin -->
    <p class="ds-measure">…</p>                           <!-- running text: never wider than the reading width -->
    <div class="ds-grid">
      <article class="ds-span-two-thirds">…</article>     <!-- 4 of 4 on a phone, 5 of 8, 8 of 12 -->
      <article class="ds-span-third">…</article>          <!-- 4 of 4, 3 of 8, 4 of 12 -->
    </div>
    <ul class="ds-tiles">…</ul>                           <!-- cards that wrap: as many 256px columns as fit -->
  </div>
</main>
```

| Class | Does |
|---|---|
| `.ds-page` | `max-width: calc(container + 2 × margin)`, `padding-inline: layout.margin`, centred. Wider screens get wider margins |
| `.ds-grid` | `repeat(layout.columns, minmax(0, 1fr))` with `layout.gutter`; items get `min-width: 0` |
| `.ds-span-full` · `-half` · `-third` · `-two-thirds` · `-quarter` | A fraction of the grid the item is in, in whole columns (table in the [guide](GUIDE.md#the-page-grid)) |
| `.ds-measure` | `max-width: layout.measure.reading` (34rem) |
| `.ds-tiles` | `repeat(auto-fill, minmax(min(100%, layout.tile.min), 1fr))`, gaps `stack.lg` / `inline.lg` — follow density |
| `.ds-region` | Makes an element a size container: a `.ds-grid` inside takes the grid of its width. Shell regions already are |

**Grids follow their region.** Beside the open navigation at 1024px the main region is 768px wide, so its `.ds-grid` gets the
`md` grid — 8 columns of 65px — not 12 of 35px. That happens in `tokens.css` with container queries on the shell regions;
spans follow too. Never write a window media query to change a grid inside a region. If you split a page yourself (a list
beside a preview), put `.ds-region` on each side.

Need a fraction the classes don't have? Raise it as a design-system change rather than writing spans in window media
queries — those break inside a region.

## Widths

| Content | Use | Never |
|---|---|---|
| Paragraphs, help, articles, forms | `.ds-measure` / `max-w-reading` | a px `max-width`, or the page width |
| A page's content | `.ds-page` | `width: 1200px`, `max-width: 1100px` |
| A table | the region's full width; wider tables scroll inside a container with `tabindex="0"`, `role="region"` and a name | `overflow-x: hidden` on `body` |
| A pane | `var(--ds-layout-pane-nav)`, `w-aside` … (the shell does it) | a px track of your own |
| Cards that wrap | `.ds-tiles` | `minmax(240px, 1fr)` hand-set |

```html
<div class="table-wrap" tabindex="0" role="region" aria-labelledby="t-caption" style="overflow-x: auto">
  <table><caption id="t-caption">Projects</caption>…</table>
</div>
```

`width: 100vw` includes the scrollbar and scrolls the page sideways on desktops with one — use `100%` (or nothing).

## Sticky bars and focus

`tokens.css` sets `html { scroll-padding-top: var(--ds-layout-scroll-padding-top) }`: `max(header height, the same in rem)`,
so when the browser scrolls a focused item into view it stops below the header — and further below at bigger text sizes,
because the header's labels grow too (WCAG 2.4.11).

- Another sticky bar under the header adds its height: `html { scroll-padding-top: calc(var(--ds-layout-scroll-padding-top) + 3rem); }`.
- Keep that bar under the same height condition as the header: `@media (min-height: 30em) { .filters { position: sticky; top: var(--ds-layout-header-height); } }`.
- A header that can wrap even in a tall window? Measure it and set the padding from its real height:

```js
const header = document.querySelector('[data-shell="header"]');
new ResizeObserver(([e]) => document.documentElement.style.scrollPaddingTop = `${e.borderBoxSize[0].blockSize}px`).observe(header);
```

## Names: Figma → CSS → Tailwind

| Figma variable | CSS variable | Tailwind |
|---|---|---|
| `layout/margin` | `--ds-layout-margin` | `px-margin`, `mx-margin` |
| `layout/gutter` | `--ds-layout-gutter` | `gap-x-gutter` |
| `layout/columns` | `--ds-layout-columns` | — (use `.ds-grid`) |
| `layout/container/max` | `--ds-layout-container-max` | `max-w-page` (use `.ds-page` for the margins) |
| `layout/measure/reading` | `--ds-layout-measure-reading` | `max-w-reading` |
| `layout/pane/nav`, `layout/pane/aside` | `--ds-layout-pane-nav`, `--ds-layout-pane-aside` | `w-nav`, `w-aside` |
| `layout/tile/min` | `--ds-layout-tile-min` | — (use `.ds-tiles`) |
| `layout/header/height` | `--ds-layout-header-height` | `min-h-header` |
| `layout/scroll-padding/top` | `--ds-layout-scroll-padding-top` | `scroll-pt-header` (set on `<html>` already) |
| `breakpoint/md` · `lg` · `xl` | `--ds-breakpoint-md` … (documentation only — media queries can't read variables) | `md:` `lg:` `xl:` |

## Moving an existing product to ds layout

1. **Find what's there.** `npm run lint:layout -- path/to/your-app/src` lists fixed widths, page edges, breakpoints of their
   own, text without a measure, bare `1fr` tracks, reordering, hidden overflow and scroll padding, with line numbers.
2. **Map the frame first.** Put the screen in the shell: what is navigation, what is the task, what supports it. Delete the
   media queries that showed and hid sidebars — the shell does it.
3. **Then the widths.** Text and forms get `.ds-measure`, the page `.ds-page`, card lists `.ds-tiles`, aligned blocks `.ds-grid`
   with spans. Remove every px `width` above 320px.
4. **Then the breakpoints.** Every remaining media query moves to 37.5em, 64em or 90em, `min-width`. If a component breaks
   between two of them, let it wrap or let it follow its region instead of adding a width.
5. **Check the rendered page.** `npm run audit:layout -- page.html` renders it at 320, 600, 1024, 1440 and 1920px in every
   density, at 400% zoom (320 × 256) and at 200% text (the browser setting), and reports sideways scrolling, grids with
   columns under 40px, regions drawn out of code order, lines over 80 characters, focus hidden under sticky bars while
   tabbing both ways, and whether the drawer opens, leaves the page visible, takes focus and closes with Escape.
   `--shots dir` saves what it saw.

## Checking in CI

The layout checker exits with code 1 on any error. It has no dependencies — copy `engine/src/lint/layout-lint.js` into your
repo next to the `layout.contract.json` you ship:

```yaml
# .github/workflows/layout.yml
name: Layout
on: pull_request
jobs:
  layout:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: node tools/layout-lint.js src --contract design/layout.contract.json
```

A file can switch off named rules with a comment, for example on a specimen page: `<!-- ds-lint-ignore: LR-03 -->`. Use it
rarely and say why next to it.

**What the checker can't see:** it reads source, one rule or class list at a time. Whether an element is running text when
its class doesn't say so, whether a scrolling container is really needed, focus hidden by a bar you made sticky in
JavaScript, and layouts that only break at one width or density need the layout audit or a review (the
[review prompt](../../04-ai-layer/layout/prompts/review-layout.md) is written for those).

## Pull-request checklist

- [ ] Page edges use `layout.margin` (`.ds-page` or `px-margin`); no container has a fixed width.
- [ ] Running text and forms are within `layout.measure.reading`.
- [ ] Media queries are 37.5em, 64em or 90em, `min-width` — or Tailwind `md:` `lg:` `xl:`; none inside regions.
- [ ] Grids use `.ds-grid` with `.ds-span-*` or `.ds-tiles`; any other grid tracks are `minmax(0, 1fr)`, flex children that hold
      text have `min-width: 0`.
- [ ] The shell's regions are in code order; nothing is reordered with `order` or `*-reverse`.
- [ ] Sticky bars: the header uses `min-height`, extra bars add their height to the scroll padding.
- [ ] Wide tables scroll inside a focusable, named container; no `100vw`; no hidden overflow on `html` or `body`.
- [ ] `npm run lint:layout` and `npm run audit:layout` pass.

## Figma

- Open `02-foundations/figma/ds-layout-foundation.fig`. It has the Primitives (breakpoints and the spacing scale, hidden from
  publishing), Responsive (sm, md, lg, xl), Layout (widths) and Density collections, plus Color and the type styles its own
  text uses.
- A page frame set to a **Responsive** mode shows that breakpoint's columns, gutter and margin; a region frame beside a pane
  sets its own mode for its own width — the same rule as the container queries in code.
- Widths (`layout/*` in the Layout collection) are scoped to width and height; gutter and margin to gaps and padding;
  `layout/columns` is kept out of pickers (it is a count).

## When something's missing

- **Another pane** → add it in the engine config (`layout.panes`): a name by job (`layout.pane.<job>`), a width in px
  (multiple of 8, 160–480), the breakpoint where it goes inline (`md`, `lg`, `xl`) and a side. The build adds every pane up
  at every breakpoint and fails (L3) if the main region would lose its reading line or its grid. With the built-in panes
  open at `xl`, a third pane can be at most 192px.
- **A wider or narrower navigation or supporting pane** → `layout.nav` (160–272px), `layout.aside` (240–480px).
- **Bigger or smaller tiles** → `layout.tile` (160–320px).
- **A fifth breakpoint, more columns, a wider reading width** → not in the config on purpose: they are what every check
  is built on. Raise it as a design-system change.
