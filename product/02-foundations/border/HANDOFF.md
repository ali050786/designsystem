# Border · developer handoff

How to take ds borders from Figma into code and keep them correct. Read the [guide](GUIDE.md) first if you haven't — this
page assumes you know the four jobs, which colours go with each, and why states widen. A working page that uses everything
below is in [demo/](demo/index.html): it has switches for the control width (1px or 2px, two builds of `tokens.css`), the
density and a forced-colours preview, and reads back the widths and paddings the page is using.

---

## What you get

All generated by the engine (`npm run build` → `engine/out/<name>/`). Never edit them by hand.

| File | What it is | Who uses it |
|---|---|---|
| `tokens.css` | The scale (`--ds-border-width-1` … `-3`), the jobs (`--ds-border-width-line`, `-control`, `-state`, `-indicator`), the focus ring (`--ds-focus-ring-width`, `-offset`, `-color`), the ring on `:focus-visible`, the forced-colours rules and `.ds-join` (parts overlap by one control border) | Every web project |
| `tailwind.theme.css` | `border-line`, `border-control`, `border-state`, `border-indicator` and every side form (`border-b-line`, `border-s-indicator`, `divide-y-line` …) | Tailwind projects |
| `tokens.json` | All tokens in the W3C design-token format | Other platforms, Style Dictionary |
| `figma/Border.Value.tokens.json` | The Border collection for Figma, scoped to stroke weight | Design |
| `ai/rules/border.md`, `ai/border.contract.json` | The border rulebook and contract for AI tools and the border checker | AI tools, the border checker |
| `report.html`, `report.json` | Every border check (B1–B6, F2) item by item; border colour pairs are in C3 | Reviews, audits |

## Install

The same `tokens.css` as the other foundations — nothing extra to load. Tailwind v4:

```css
@import "tailwindcss";
@import "./tokens.css";
@import "./tailwind.theme.css";
```

## Jobs and their colours

Pick the job by what the line does, then one of its colours. Values for this build (`"border": { "control": 1 }`):

| Job | CSS | Tailwind | Width | Colours |
|---|---|---|---|---|
| structure | `var(--ds-border-width-line)` | `border-line` | 1px | `--ds-color-border-subtle` (dividers), `--ds-color-border-default` (cards, frames, menus) — decorative |
| a control's edge | `var(--ds-border-width-control)` | `border-control` | 1px | `--ds-color-border-input` (fields, checkboxes, radios), `--ds-color-action-secondary-border` (buttons), `--ds-color-border-strong` — 3:1 |
| a state | `var(--ds-border-width-state)` | `border-state` | 2px | `--ds-color-border-selected`, `-danger`, `-warning`, `-success` — 3:1, always with a second cue |
| the current item | `var(--ds-border-width-indicator)` | `border-s-indicator`, `border-b-indicator` | 3px | `--ds-color-border-selected` — one side only |

```css
.card  { border: var(--ds-border-width-line) solid var(--ds-color-border-default); }
.rows li + li { border-block-start: var(--ds-border-width-line) solid var(--ds-color-border-subtle); }
input  { border: var(--ds-border-width-control) solid var(--ds-color-border-input); }
.btn   { border: var(--ds-border-width-control) solid transparent; }        /* every control has a border: see forced colours */
.btn-secondary { border-color: var(--ds-color-action-secondary-border); }
```

No `1px`, no `0.5px`, no `rem`: the checker flags them (BR-01, BR-03). Tailwind's own `border`, `border-2` and `ring-*` are
flagged too (BR-04) — use the job utilities.

## States

A state widens the border to its job, adds a second cue, and takes the extra width off the padding so nothing moves:

```css
input[aria-invalid="true"] {
  border-width: var(--ds-border-width-state);
  border-color: var(--ds-color-border-danger);
  padding-inline: calc(var(--ds-space-inset-md) - (var(--ds-border-width-state) - var(--ds-border-width-control)));
}
.choice:has(input:checked) {                       /* a selected card: outline line → state */
  border-width: var(--ds-border-width-state);
  border-color: var(--ds-color-border-selected);
  padding: calc(var(--ds-space-inset-lg) - (var(--ds-border-width-state) - var(--ds-border-width-line)));
}
```

The second cue is markup: `aria-invalid` + `aria-describedby` pointing at a message with an icon; a check mark on a
selected card; bold text on the current tab. Tailwind: `ps-[calc(var(--spacing-inset-md)-var(--ds-border-width-indicator))]`
is accepted by the spacing checker (a token minus a border width).

**The current-item bar is drawn only on the current item.** Don't give every tab a transparent bar and colour the current
one — forced colours draw transparent borders, so every tab would show a bar:

```css
[role="tab"] { position: relative; }
[role="tab"][aria-selected="true"]::after { content: ""; position: absolute; inset-inline: 0; inset-block-end: 0;
  border-block-end: var(--ds-border-width-indicator) solid var(--ds-color-border-selected); }
.nav a[aria-current="page"] { border-inline-start: var(--ds-border-width-indicator) solid var(--ds-color-border-selected);
  padding-inline-start: calc(var(--ds-space-inset-md) - var(--ds-border-width-indicator)); }
```

Hover and press change the fill, never the width.

## Focus rings

`tokens.css` draws the ring on `:focus-visible`: `outline: 2px solid var(--ds-focus-ring-color); outline-offset: 2px`.
Nothing to add; never `outline: none` (BR-05). A full-width row or a table cell with no room around it keeps the outline
and draws it inside:

```css
.list a:focus-visible { outline-offset: calc(-1 * var(--ds-focus-ring-width)); }
```

If a design insists on a box-shadow ring, keep a transparent outline beside it, or forced colours show no ring at all:

```css
.chip:focus-visible { outline: var(--ds-focus-ring-width) solid transparent; box-shadow: 0 0 0 var(--ds-focus-ring-width) var(--ds-focus-ring-color); }
```

## Joined parts

```html
<div class="ds-join" role="group" aria-label="View">
  <button class="btn btn-secondary" aria-pressed="true">List</button>
  <button class="btn btn-secondary" aria-pressed="false">Board</button>
</div>
```

`.ds-join` overlaps each part with the one before by `var(--ds-border-width-control)`, so every seam is one line (two 1px
borders would make a 2px seam — the width of a selected state). It lifts the hovered, pressed, selected, checked and
invalid part above its neighbours so its whole border shows, and the focused part above that. Don't write
`margin-inline-start: -1px` yourself (BR-10). Tables: `border-collapse: collapse`, or lines on one side of each row.

## Forced colours

Windows contrast themes replace every colour, remove box-shadows and background images, and draw borders and outlines
(transparent ones too) in the system text colour. `tokens.css` already:

- gives the focus ring the system's `Highlight`;
- outlines `aria-selected`, `aria-current`, `aria-pressed`, `aria-checked` and labels around a checked radio in
  `SelectedItem` (inside the element, state width), because their fills are gone;
- turns disabled controls `GrayText`.

You: give every control a border (transparent if none shows); never draw a boundary or a ring with box-shadow alone; show
selection with those attributes or with a real border; keep `forced-color-adjust: none` for colour swatches and charts.

Test on Windows (Settings → Accessibility → Contrast themes), in Chrome or Edge DevTools (Rendering → Emulate CSS media
feature forced-colors), or with the audit below — it uses Chromium's real forced-colour rendering. The demo's
"forced (preview)" switch is an imitation for people without either.

## Heavier controls

Products whose people need fields to stand out set `"border": { "control": 2 }`: controls become 2px, states 3px, the
indicator 3px; structure lines stay 1px. Nothing changes in component code — that's why widths are jobs. The demo
switches between the two builds (`tokens.css`, `tokens-control-2.css`).

## Adding a job

```json
{ "border": { "control": 1, "roles": [
  { "name": "border.width.drop-zone", "width": 2, "color": "color.border.strong", "identifies": true, "style": "dashed",
    "description": "The edge of an area files can be dropped on" } ] } }
```

The build refuses names by look (`thick`, `hairline`), widths off the scale or below a pixel, colours that aren't border
roles; B2 fails a job with the same width, colour, style and sides as another, B3 a job that identifies something in a
colour under 3:1.

## Moving an existing product to ds borders

1. **Find what's there.** `npm run lint:border -- path/to/src` lists hard-coded and rem widths, hairlines, primitives,
   Tailwind's own widths and rings, removed focus rings, box-shadow lines, filled controls without a border, control
   lines in decorative colours, states shown by colour alone or that move content, hand-made overlaps and redefined
   variables.
2. **Map every line to a job.** Dividers and card outlines → line; field, checkbox and secondary-button edges → control;
   selected, invalid, valid → state; the current tab or page → indicator. Delete lines that space or a surface already do.
3. **Fix the states.** Widen to the state width, add the second cue, compensate the padding.
4. **Check the rendered page.** `npm run audit:border -- page.html` renders it at 1280 and 320px and at 200% text, normally
   and in forced colours, and reports widths that don't follow the control width, widths that grow with text, control
   edges under 3:1, doubled seams, lines drawn with box-shadow, states that move content or show by colour alone, controls
   that lose their edge in forced colours, states that disappear there, and focus rings missing in either mode.
   `--shots dir` saves what it saw.

## Checking in CI

The border checker exits with code 1 on any error and has no dependencies — copy `engine/src/lint/border-lint.js` next to
the `border.contract.json` you ship:

```yaml
      - run: node tools/border-lint.js src --contract design/border.contract.json
```

The audit needs Playwright (`npm i -D playwright`) and a built page; run it on the pages that matter (forms, tables,
navigation) before release.
