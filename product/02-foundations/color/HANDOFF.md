# Colour · developer handoff

How to take ds colour from Figma into code and keep it correct. Read the [guide](GUIDE.md) first if you haven't — this
page assumes you know what roles, pairs and modes are. A working page that uses everything below is in [demo/](demo/index.html).

---

## What you get

All generated by the engine (`npm run build` → `engine/out/<name>/`). Never edit them by hand.

| File | What it is | Who uses it |
|---|---|---|
| `tokens.css` | Every token as a CSS variable, Light/Dark switching, and a small base layer (page colours, focus ring, links) | Every web project |
| `tailwind.theme.css` | Maps the roles into Tailwind v4 (`bg-bg-surface`, `text-fg-muted` …) | Tailwind projects |
| `tokens.json` | All tokens in the W3C design-token format (DTCG) | Other platforms, Style Dictionary, Terrazzo |
| `figma/*.tokens.json` | One file per collection and mode, for Figma | Design |
| `report.html`, `report.json` | Every check and every pair, measured | Reviews, audits |
| `ai/rules/color.md`, `ai/color.contract.json` | The colour rulebook and contract for AI tools | AI tools, the colour checker |

## Install

**Plain CSS.** Load `tokens.css` before your own styles.

```html
<link rel="stylesheet" href="/css/tokens.css">
<link rel="stylesheet" href="/css/app.css">
```

**Tailwind v4.** In your main CSS file, in this order:

```css
@import "tailwindcss";
@import "./tokens.css";
@import "./tailwind.theme.css";
```

The base rules in `tokens.css` sit in the `base` layer. With Tailwind they join Tailwind's own base layer, after Preflight,
so your utility classes still win (tested with Tailwind 4.3). Without Tailwind, any of your normal CSS wins. They are
defaults, never overrides.

## Light and Dark

Modes are switched on `<html>`. Without the attribute the page follows the system setting.

```html
<html data-theme="light">  <!-- or "dark"; remove it to follow the system -->
```

To remember a choice without a flash of the wrong mode, set the attribute before the stylesheet loads:

```html
<script>
  try { const t = localStorage.getItem('ds-theme'); if (t === 'light' || t === 'dark') document.documentElement.setAttribute('data-theme', t); } catch (e) {}
</script>
```

Then switch it from your UI by setting or removing `data-theme` (the demo has a three-way Light / Dark / System control).
Never write separate dark colours (`[data-theme=dark] .card { … }`): every role already changes with the mode.

The same pattern works for `data-density` (comfortable / default / compact) and `data-motion` (full / reduced).

## Names: Figma → CSS → Tailwind

One rule: take the Figma variable name, replace `/` with `-`, and prefix it.

| Figma variable | CSS variable | Tailwind class |
|---|---|---|
| `color/bg/surface` | `var(--ds-color-bg-surface)` | `bg-bg-surface` |
| `color/fg/muted` | `var(--ds-color-fg-muted)` | `text-fg-muted` |
| `color/border/input` | `var(--ds-color-border-input)` | `border-border-input` |
| `color/action/primary/bg-hover` | `var(--ds-color-action-primary-bg-hover)` | `hover:bg-action-primary-bg-hover` |
| `color/data/chart-1` | `var(--ds-color-data-chart-1)` | `fill-data-chart-1`, `bg-data-chart-1` |

The doubled word in Tailwind (`bg-bg-…`, `border-border-…`) is deliberate: the first part is Tailwind's utility, the second
is the role's group. It keeps one name everywhere. In Figma's Dev Mode, the variable name on the selected layer is the
name to use — the `.fig` export doesn't carry code syntax, so read the name and apply the rule above.

Tailwind generates every utility for every role (`text-bg-canvas` exists). Only the combinations in the pair contract are
supported; the colour checker tells you when you've used one that isn't.

## Patterns

Each pattern is in the [demo](demo/index.html), working, in both modes.

### Surfaces and elevation

Use the elevation classes for things that sit above the page; each takes the whole level (surface, shadow, edge and
place in the stacking order). The Elevation package (`02-foundations/elevation/`) has the rules.

```html
<article class="ds-raised">…</article>                            <!-- a card -->
<header class="ds-sticky">…</header>                              <!-- the page header -->
<div class="ds-floating" popover id="menu">…</div>                <!-- a menu -->
<dialog class="ds-modal" aria-labelledby="t">…</dialog>           <!-- a dialog: open with showModal(); ::backdrop is the scrim -->
```

### Buttons

Every state has a role. Disabled uses the disabled roles whatever the kind.

```css
.btn-primary          { background: var(--ds-color-action-primary-bg); color: var(--ds-color-action-primary-fg); }
.btn-primary:hover    { background: var(--ds-color-action-primary-bg-hover); }
.btn-primary:active   { background: var(--ds-color-action-primary-bg-pressed); }
.btn-secondary        { background: var(--ds-color-action-secondary-bg); color: var(--ds-color-action-secondary-fg);
                        border: 1px solid var(--ds-color-action-secondary-border); }
.btn-ghost            { background: var(--ds-color-action-ghost-bg); color: var(--ds-color-action-ghost-fg); }
.btn-ghost:hover      { background: var(--ds-color-action-ghost-bg-hover); }
.btn-icon             { background: var(--ds-color-action-ghost-bg); color: var(--ds-color-fg-icon); } /* icon-only */
.btn:disabled         { background: var(--ds-color-action-disabled-bg); color: var(--ds-color-action-disabled-fg);
                        border-color: var(--ds-color-action-disabled-border); }
```

Disabled colours are exempt from contrast, so say nearby why something is disabled ("Publish is off until the checks pass").
One primary button per view.

### The focus ring

`tokens.css` draws it for you: 2px `border.focus`, 2px gap, on `:focus-visible`. Don't add focus styles and never remove
outlines (`outline: none`, `outline-none`). If a custom control hides the real input, put the ring on what people see:

```css
.segmented label:has(input:focus-visible) {
  outline: var(--ds-focus-ring-width) solid var(--ds-focus-ring-color);
  outline-offset: var(--ds-focus-ring-offset);
}
```

### Inputs and errors

```css
.field input        { background: var(--ds-color-bg-surface); color: var(--ds-color-fg-default); border: 1px solid var(--ds-color-border-input); }
.field input::placeholder { color: var(--ds-color-fg-subtle); }
.field input[aria-invalid="true"] { border-color: var(--ds-color-border-danger); }
.field .error       { color: var(--ds-color-fg-danger); }  /* with an icon and words: "✕ That date doesn't exist." */
```

Connect the message with `aria-describedby`. Never use `border.subtle` or `border.default` on a control — they're decorative.

### Hover, pressed, selected

| Where | Hover / pressed |
|---|---|
| Rows and items on a plain surface | `bg.surface-hover` / `bg.surface-pressed` (solid — any text role can sit on it) |
| Ghost and icon buttons on canvas, surface or sunken | `action.ghost.bg-hover` / `-pressed` (translucent tints) |
| Items inside menus, popovers, dialogs, raised cards | `bg.item-hover` / `bg.item-pressed` (solid) |

Selected rows use `bg.selected` **plus** a check or bold label, and the right ARIA (`aria-selected`, `aria-current`,
`aria-pressed`). Colour alone never says "selected".

### Status messages and badges

```css
.msg-warning        { background: var(--ds-color-bg-warning-subtle); color: var(--ds-color-fg-default); }
.msg-warning .icon  { color: var(--ds-color-fg-warning); }
.badge-danger       { background: var(--ds-color-bg-danger); color: var(--ds-color-fg-on-danger); }
```

Words first ("Upload failed."), then an icon, then colour. Links inside messages use `fg.link` as normal.

### Good and bad change

Colour by meaning, arrow by direction. Decide per metric whether higher is better.

```js
// From the demo: returns e.g. ▼ −0.9% in fg.positive for a falling error rate.
function change(delta, { higherIsBetter = true, unit = '%' } = {}) {
  if (delta === 0) return `<span class="change-flat">– no change</span>`;
  const up = delta > 0, good = up === higherIsBetter;
  return `<span class="${good ? 'change-good' : 'change-bad'}">${up ? '▲' : '▼'} ${up ? '+' : '−'}${Math.abs(delta)}${unit}</span>`;
}
```

```css
.change-good { color: var(--ds-color-fg-positive); }
.change-bad  { color: var(--ds-color-fg-negative); }
.change-flat { color: var(--ds-color-fg-muted); }
```

### Charts

Use series in order — `data.chart-1`, then `-2` … — and label them (a legend or direct labels, plus a text alternative).
Axes use `data.axis`, gridlines `data.gridline`, labels `fg.muted`.

For SVG, set `fill` from CSS classes and the chart follows the mode automatically. For canvas-based libraries, read the
values and redraw when the mode changes:

```js
const role = (name) => getComputedStyle(document.documentElement).getPropertyValue(`--ds-color-${name}`).trim();
const palette = () => [1, 2, 3, 4, 5, 6, 7, 8].map((n) => role(`data-chart-${n}`));
new MutationObserver(() => chart.update({ colors: palette() }))
  .observe(document.documentElement, { attributes: true, attributeFilter: ['data-theme'] });
matchMedia('(prefers-color-scheme: dark)').addEventListener('change', () => chart.update({ colors: palette() }));
```

## Moving an existing product to ds colour

Do it screen by screen, not file by file — a role is chosen by its job, which you can only see on the screen.

1. **Find what's there.** `npm run lint:color -- path/to/your-app/src` (files or folders) lists every raw colour, shade and unsupported pair, with line numbers.
2. **Pick roles by job, not by nearest colour.** For each colour, ask the decision-guide questions (the guide's [Choosing and using colour](GUIDE.md#choosing-and-using-colour)). A grey that is "close to" `fg.muted` but used for timestamps is `fg.subtle`.
3. **Replace, then delete dark-mode overrides.** Once a component uses roles, its `[data-theme=dark]` or `prefers-color-scheme` rules are dead weight — remove them.
4. **Fix the pairs the checker reports.** Usually a solid fill missing its on- colour, a decorative border on an input, or a tint inside a menu.
5. **Check the rendered page.** `npm run audit:page -- page.html --click "#open-menu,#open-dialog"` measures every piece of text, input outline and focus ring in Light and Dark, including open menus and dialogs.
6. **Need a colour that has no role?** Don't use a shade. Check [Choosing and using colour](GUIDE.md#choosing-and-using-colour) again; if nothing fits, add a role in the engine config ([Modes and brands](GUIDE.md#modes-and-brands)) so it is measured like the rest.

## Checking in CI

The colour checker exits with code 1 on any error, so it can gate a pull request. It has no dependencies — copy
`engine/src/lint/color-lint.js` into your repo (here, `tools/`) next to the `color.contract.json` you ship:

```yaml
# .github/workflows/colour.yml
name: Colour
on: pull_request
jobs:
  colour:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: node tools/color-lint.js src --contract design/color.contract.json
```

Update the contract whenever you update `tokens.css`, so the checker and the tokens always match.

**What the checker can't see:** it reads one CSS rule or one class list at a time. Text that inherits its background
from a parent, colour-only meaning in content, and two primary buttons in one view need the page audit or a review
(the [review prompt](../../04-ai-layer/color/prompts/review-colour.md) is written for exactly those).

## Pull-request checklist

- [ ] No hex, rgb(), named colours, Tailwind palette classes or shade variables — roles only.
- [ ] Every text, icon and outline sits on a background listed for it, including hover, pressed and selected states.
- [ ] Solid fills use their on- colour.
- [ ] Inputs and controls use `border.input` / `border.strong`.
- [ ] Hover inside menus, popovers and dialogs uses `bg.item-hover`.
- [ ] Focus ring untouched; tabbing through the page shows it on every control.
- [ ] Status has words or an icon; links are underlined; changes have an arrow or sign, coloured by good/bad.
- [ ] One primary action per view.
- [ ] Checked in Light and Dark (`npm run audit:page`).
- [ ] `npm run lint:color` passes.

## When something's missing

- **A colour you need doesn't exist** → add a role in the engine config (`color.roles`); see [Modes and brands](GUIDE.md#modes-and-brands) in the guide. The build measures it.
- **A pair you need isn't listed** → for a product role, add it to the role's `on` / `carries` list; for a built-in role, ask for the pair to be added to the engine (it is then measured on every build). Until then, rethink the design — unlisted pairs aren't supported.
- **The brand changes** → change `color.brand` in the engine config and rebuild. Nothing in code is renamed.
